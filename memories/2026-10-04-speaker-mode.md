# 扬声器模式：已证明的和没证明的

## 结论（已更新 · 这条覆盖本文件早先的版本）

**功能已通，用户在 iPhone 上亲自听到了声音。** 真机端到端：

```
[ ok ] 4c. the received audio is NOT silence (pcmRms=1965)
    ... pcmRms=1965 pcmPeak=8856 ...      ← 8856 = 测试音符的振幅
```

**我早先写的「听到的是静音」是错的。** 根因：`SpeakerPlayer.enqueue`
**根本没有测量代码** —— 它把包丢进环形缓冲、计数器加一、就返回了，
而 `receivedRms` / `receivedPeak` / `envelope` 这些属性**声明了但从没人写**。
属性声明在一次编辑里活下来了，喂它们的代码没有，所以文件照样编译、看起来
照样完整。每一轮都打印 `pcmRms=0` 和空包络，我读成「手机收到静音」，并在
这个错误结论上建了一整套诊断。回退不是我自己做的，是并行 session 覆盖了
那个文件。

## 真机实测到的（iPhone 14 / iOS 26，Mac 真机）

| 环节 | 证据 |
|---|---|
| iOS 音频会话 | **5 步 0 失败**：`.record` ↔ `.playback` 双向交接都成功，且**不需要任何新权限** |
| Mac 采集 | **真的抓到了声音**：643 个包里 103 个非零，peak 8855 = 测试音符的振幅 |
| 传输 | 707 个包到达手机，705 个播出，0 饿死 |
| 手机的能量测量 | ✅ `pcmRms=1965` `pcmPeak=8856` —— 音频到达 |
| 用户验收 | ✅ **用户在 iPhone 上听到了声音** |

链路每一段都有证据，没有一段是靠推断的。

## 两个我判错的地方

1. **「整条链路都是静音」是错的。** 测试信号是 8 个音符带 250ms 间隔，所以**约一半的包本来
   就该是零**，我把音符间的静音读成了故障。真值是 103/643 非零。
   —— 只有**有结构的**测试信号才能区分「完整到达」和「片段到达」。

2. **「数字互相矛盾」我处理反了。** 包络在增长却打印空字符串、而 `enqueued` 在涨 ——
   这只有一个解释：**那段代码没在跑**。我却当成音频链路有问题，去查传输和编解码。
   **当两个数字互相矛盾时，先怀疑「代码没在跑」，而不是「数据有问题」。**

3. **两个电平日志都是累计平均值，我却拿它们比同一瞬间**（这条在测量代码缺失时还叠加在上面）。

## 环形缓冲索引所有权（仍然是一处真实的修复）

`readIndex` 原来被实时线程和 pump 线程**同时写**（回调在溢出时重置它，pump 推进它消费）。
两个写者意味着无符号的 `writeIndex &- readIndex` 会回绕，「够不够一包」的判断会基于
垃圾值通过。已改成每个索引只有一个写者：回调发布 `writeIndex` 和一个 `pendingDrops`
**计数**，只有 pump 推进 `readIndex`。**但要诚实说：我无法证明这就是当时听不到声音的原因**
—— 那时我看到的「包全是零」本身就是坏掉的测量。修改本身是对的（消除了一个真实的
竞态），但不要把它当成已验证的修复。
