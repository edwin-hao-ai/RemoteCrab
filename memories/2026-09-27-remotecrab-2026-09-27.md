# RemoteCrab 2026-09-27: 按住说话跨多次可用的根因(延迟收尾被跳过→串行化) + 本会话进展

# RemoteCrab / iBridge 会话记忆 — 2026-09-27 (later)

## 主线成果：hold-to-talk 现在可以连续使用多次（用户设备已验证）
用户报"输入完松手，再按住就没法说话/用几次就不能说话了"。

**根因（回归，本会话自己引入在 commit 42f8ac5）**：`VoiceRecognizer.stop()` 与
`AnalyzerVoiceEngine.stop()` 用 300ms 延迟收尾（为了让最后一个音节还进到识别器），
并用 `sessionGeneration` / `stopRequested` 守卫。当用户在松手后 300ms 内再次按下时，
新的 `start()` 会把守卫重置 → **旧的收尾整段 return 掉了** → 上一个
`SFSpeechRecognitionRequest` / `SpeechAnalyzer`、结果任务、已安装的麦克风 tap
**永远没释放**。几次之后资源耗尽，`start()` 直接失败 → 表现为"按了没反应"。

那个守卫的由来：早前收尾**错杀**过新会话（"用两次就不能用了"）。所以用"跳过收尾"
治了"第二次坏"，代价是**泄漏**，变成"几次后坏"。

**正确形态 = 串行化（不要再叠修复，这是我第 3 次改语音生命周期，按 AGENTS 规则 4 回头改模型）**：
- 收尾**必定执行**（只释放属于它自己那次会话的对象）；
- `start()` 在创建新会话前 `await` 在飞的 `teardownTask`（`VoiceEngine` 协议新增
  `waitForTeardown()`，默认 no-op）；
- `AnalyzerVoiceEngine.start()` 补上缺失的 `isStarting` 守卫。
- **通用规则：任何让 cleanup 路径提前 return 的守卫都是泄漏制造机 —— 要串行化
  (`await` task)，不要跳过。**

同一 build 还带上：never-shrink final（analyzer 记录见过的
最长 `committed+volatile`，finalizer 不能再截短尾部 → 修"最后一个字丢了"）；
PTT 手势改用 `onLongPressGesture(minimumDuration: 0, maximumDistance: .infinity,
onPressingChange:)`（`DragGesture`/`Button` 变体会在 re-render 时重启 hold）。

提交 `dcb23b0`；203 测试 + 双端编译通过；用户设备确认"好像还不错，应该没啥问题了"。
