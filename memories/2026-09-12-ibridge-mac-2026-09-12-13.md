# iBridge 真机调试与多 Mac 配对经验（2026-09-12/13）

# iBridge 真机调试 / 多语言 / 多 Mac 配对经验

## 1. “Mac 测试面板黑屏”根本不是解码 bug —— 是后置摄像头被挡住
- `CaptureEngine` 用 `.back` 摄像头；iPhone 扣在桌上时后置全黑。
- 判别方法：比较“相机被挡（黑）”vs“解码出黑帧”。已在 `H264Decoder` 加 env-gated 亮度探针：
  设 `IBRIDGE_DEBUG_FRAME_PROBE=1` 重启 receiver，日志出 `frame probe: min/max/avg`。
  真黑帧会 `max≈0`；正常画面 `avg≈140`。
- 探针用 CoreGraphics `CGContext.draw` 直接读像素：CI 的 PNG 写入被 sandbox 挡住，
  且失败的 CI `render` 会静默回 0，不可信。

## 2. Accessibility 授权
- `AXIsProcessTrusted()==false` 时 `CGEventPost` 被静默丢弃 —— 键盘/鼠标“没反应”的真因。
- 应用只在“首次启动”弹 prompt；`defaults delete com.ibridge.iBridgeReceiver ibridge.didFirstLaunch`
  可重新触发。
- 关键：用 `ditto` **原地覆盖同一路径** `/Applications/iBridgeReceiver.app`（同 bundle id + 同签名证书）
  后，辅助功能授权**保留**；但换路径/换签名会失效。
- 改完 TCC 后**重启 app** 才会读到新值（进程级缓存）。

## 3. 多语言（跟随系统语言）在 SPM + Xcode app 的正确做法
- iBridgeCore `Package.swift`: `defaultLocalization: "en"` + `resources: [.process("Resources")]`。
- 目录 `Sources/iBridgeCore/Resources/Localizable.xcstrings`（en 源 + zh-Hans），用 `Bundle.module` 解析。
- **最大的坑**：SwiftUI `Text(someString)` 走 `Text(verbatim:)`，**不翻译**；只有
  `Text("literal")`（LocalizedStringKey）或 `Text(LocalizedStringKey(var))` 才查 catalog。
  经 `IBLocale` 的 `String`、或 `func row(title: String)` 传入的文案 → 全 verbatim → 界面永远英文。
  修法：helper 参数改成 `LocalizedStringKey`；非 Text 的 String 用 `String(localized:bundle:.module)` /
  `NSLocalizedString(key, bundle:.module)`。
- `.help("literal")` / `.accessibilityLabel("literal")` 也可能被推断成 verbatim；用 `Text("...")` 包一层。
- 构建产物里应有 `iBridgeCore_iBridgeCore.bundle/Contents/Resources/{en,zh-Hans}.lproj`。
- 两个 app 的 `project-*.yml` 里 `xcodegen` 会用 `info.properties` 重写 Info.plist ——
  `CFBundleLocalizations` 必须写在 yml 里，否则被删。

## 4. macOS 工具链坑
- **macOS 没有 `timeout` 命令**（那是 GNU coreutils）；`timeout 5 dns-sd …` 静默失败，
  导致“Bonjour 好像没有广播”的假象。用后台 `&` + `sleep` + `kill`。
- **iOS 模拟器的 Bonjour 服务在宿主 Mac 的 `NWBrowser` 里发现不到**（合成网络），
  别用模拟器验证 Bonjour/配对链路。
- `simctl launch` 传环境变量要加 `SIMCTL_CHILD_` 前缀。

## 5. 多 Mac 配对（V0.4）
- Wiring：Mac 首帧 `clientHello 0x0A {name,id,token?,appVersion}`；iPhone 回
  `sessionReply 0x0B {result∈accepted|pending|busy|denied, ownerName?, token?}`。
- 策略纯函数 `PairingPolicy.decide(hello:paired:owner:)`：**有 owner 且不同 id → busy**（优先于 token 校验）；
  已配对且 token 匹配 → accepted；否则 pending。
- iPhone `accept()` 不再踢旧连接：有 owner 时对新人回 `busy` 并关闭，owner 不受影响。
- Mac 收到 busy/denied → `suppressReconnect=true`，停 3s 重连，改 30s 慢重试 + 手动 Retry。
- 无头验证：`IBRIDGE_E2E_AUTOPAIR=1` 自动批准。
- 真机结果：首次 `pending→accepted`；关 AUTOPAIR 重连 `paired:true→accepted`（token 持久化）；
  第二台 Mac `busy owner=…`，~32s 一次慢重试，owner 持续 4140+ 帧。

## 6. 两个 receiver 实例做“第二台 Mac”测试
- `open -n -a /Applications/iBridgeReceiver.app --args -ibridge.mac.id second-mac-test`
  （launch arg 覆盖 `ibridge.mac.id`）。
- 坑：两个实例共享同一 bundle 的 UserDefaults，所以 tokenStore 也是共享的 →
  第二实例会带着“第一个 Mac 的 token”发 `paired:true`。真实第二台 Mac 是独立 UserDefaults，
  会是 `paired:false`。但 busy 判定优先看 owner id，所以不影响 busy 路径的验证。
